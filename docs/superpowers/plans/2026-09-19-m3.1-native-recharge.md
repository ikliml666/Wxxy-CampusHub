> 2026-09-19（会话 `sess-36e5d8e0`）· 分支 `feat/sess-36e5d8e0-m3-card-electricity`
> **用户 2026-09-19 裁决**：「充值还是不要使用官方界面，我们直接使用对应的验证以及接口，同时声明风险」；配套裁决：**充值验证由用户自己在真机试充**（我实现 + 静态验证，绝不真下单）；**内嵌官方页面移除**，保留「去官网充值」兜底按钮。
> 上游事实：本文件 §1（两轮 bundle 逆向，2026-09-19 实测，全匿名）。
> **For agentic workers:** 用 `superpowers:subagent-driven-development` 执行；步骤用 `- [ ]` 跟踪。

**Goal:** 让「电费充值」在客户端内闭环完成——选房间、填金额、过一道支付校验（免密或安全键盘）、拿到结果，全程不跳官方页面；同时在界面上把风险讲清楚。

**Architecture:** 协议实现落在 `crates/campus-synjones/src/recharge.rs`（新增），命令层加 `commands/electricity.rs` 的充值命令组；前端在 `PowerPanel` 现有「房间 → 余额」流程之后接支付步骤。**客户端只做转发，不做任何金额/密码的本地"加工"**。

**Spec:** 本文件 §1 即 spec（协议细节以它为准）。

## Global Constraints（**红线，违反即返工**）

1. **客户端绝不接触真实卡密码**：服务端下发的 `passwordMap[uuid] = keys` 是「显示字符序列」，而提交给服务端的 `password` 是**用户点击的键位下标序列**（位置编码）。因此：
   - 只转发下标序列 + uuid；
   - **绝不把 `keys` 还原成真实密码**、**绝不落盘/打日志/上报**、**绝不用它回填任何输入框**（误把显示字符当密码提交 = 明文泄露用户密码）；
   - `keys`/`uuid` 只在内存里存活到该笔支付结束。
2. **不碰金额语义**：金额以用户输入为准、由服务端校验（`retain_money`/`maxmoney`/`layout` 仅用于前端提示与快捷金额），客户端**不自行改写金额**。
3. **副作用请求不重试**：`paystep:0` 建单与提交支付是副作用请求，**超时不得重试**（30s 全局超时），一律以 `getpayinfo` 的 `order.status` 兜底判定。
4. **轮询必须有上限**：官方实现是 2s 无限轮询、只在组件销毁时清理；我们**加最大次数/总时长上限**，并在离开页面时清理。
5. **拒绝跳转分支**：响应里若出现 `webUrl` / `paysubmit` / `paymentcashierStr` / `qrCodeUrl`，一律**不实现、直接报错退出**（这些是第三方渠道或 HTML 注入路径，会破坏客户端闭环，且 `document.forms[0].submit()` 在 Tauri 里不可控）。
6. **失败清理**：失败/放弃/超时后调 `POST /charge/order/deleteOrder` 清理未支付订单；进入充值流程前先检查是否有遗留未支付订单。
7. 凭据/红线沿用 M3：token 只在内存；生活数据（卡号等）不落盘、不进日志。

## 一、侦察事实（2026-09-19，两轮 bundle 逆向）

### 1.1 两条链路对比（**决定选 App 口径**）

| | PC 版 `/charge-pc` | **App 版 `/charge-app`（采用）** |
|---|---|---|
| 下单 | 需 SHA256 签名（`APP_ID=56321`、`SECRET_KEY=0osTIhce7uPvDKHz6aa67bhCukoYl4`、`TIMESTAMP`/`NONCE`、键排序拼接后大写 hex） | **无签名**，仅 Basic + bearer |
| 提交方式 | 动态 form `POST /charge/order/thirdOrder`，`target="_self"` **整页跳走** | `POST /blade-pay/pay`（ajax JSON） |
| 结果可得性 | **客户端拿不到**（页面被服务端接管） | **拿得到**：`data.orderid` + `order.status` 轮询 |

→ 结论：**按 App 口径实现**。PC 签名链路仅记录备查（若将来 App 接口变更可回退，签名算法已完整固化在 §1.4）。

### 1.2 头组（所有支付相关请求）

```
Authorization: Basic <base64("charge:charge_secret")>   ← 公开硬编码常量；实现时以 bundle 原文逐字核对，勿按本文手抄
synjones-auth: bearer <access_token>
Content-Type: application/x-www-form-urlencoded
```
> Basic 值 = `charge:charge_secret` 的 base64（公开常量，非机密）。**不发送** `synAccessSource`（App bundle 全文无此参数）。

### 1.3 支付状态机（App 口径，**照此实现**）

| 步 | 请求 | 关键参数 | 响应 |
|---|---|---|---|
| ① 建单 | `POST {BASE}/blade-pay/pay` | `feeitemid, tranamt, flag:"choose", source:"app", paystep:0, third_party` | `data.orderid`（`data.orderflag=="results"` 时直接进结果） |
| ② 取支付方式 | `GET {BASE}/charge/pay/getpayinfo?orderid=` | — | **顶层** `{order:{status,payexpdate,tranamt,…}, payList:[…]}` |
| ③ 查账户（需密码时） | `POST /blade-pay/pay` | `orderid, paystep:2, paytype, paytypeid[, accountno]` | `data.accountno[]` / `data.ccctype[]{ccctype,balance}` / **`data.passwordMap{uuid:[10 个显示字符]}`** |
| ④ 提交支付 | `POST /blade-pay/pay` | `orderid, paystep:2, paytype, paytypeid, accountno, ccctype, isWX:0` + **免密时无**，需密码时 `password`(下标序列) + `uuid` | 账户支付预期落到「无上述跳转字段」的兜底分支 → 进结果 |
| ⑤ 结果 | `GET /charge/pay/getpayinfo?orderid=` | — | `order.status`：**0=待支付、1=已完成** |
| ⑥ 清理 | `POST /charge/order/deleteOrder` | `orderid` | 无 |

要点：
- **`payList` 不在 `paystep` 里**，在 ② 的顶层（最易误判处）。
- `paytype` ← `payList[i].code`；`paytypeid` ← `payList[i].payid`；默认取 `payList[0]`。
- **只保留 `code ∈ {ACCOUNT, ACCOUNTTSM}`**（校园卡/电子账户），做展示层过滤；**不要**照抄官方「只剩一种支付方式就自动提交」的行为，也**不要伪造 code**。
- **免密判据只有一条**：`payList[i].nopassword === 1` → 免密（提交体不含 password/uuid）；`0`/falsy → 需密码；其他真值官方是**死分支**（什么都不做），我们按「需密码」处理并留注释。
- 密码弹层语义：标题「请输入校园卡查询密码」，**6 位**，点满自动提交。
- `flag` 电费恒 `"choose"`。
- `third_party`：**电费专用**，App 版形如 `"<sceneinfo>-<选中 id 列表>-<金额列表>"`（与 PC 版的 JSON 形态不同，勿混用）；`sceneinfo` 来自 ③ 之前的房间级联（`getThirdData` 的末级选择）。

### 1.4 PC 签名算法（备查，本次不实现）

```
sign(data, app_id="56321", secret="0osTIhce7uPvDKHz6aa67bhCukoYl4"):
  data += {APP_ID: app_id, TIMESTAMP: yyyyMMddHHmm+两位, SIGN_TYPE: "SHA256", NONCE: base36 随机}
  keys = 字典序排序(data.keys) 跳过 SIGN/SECRET_KEY
  s = 每个 k 拼 "k=v&"（跳过 falsy 值；数字 0 保留）
  s += "SECRET_KEY=" + secret          # 不参与排序，直接缀尾
  data.SIGN = SHA256(s).hex().toUpperCase()
```
（实测 `TIMESTAMP` 生成有毫秒/秒混淆的线上 bug；已验证复现一致。）

## 二、实现设计

### 2.1 后端（`crates/campus-synjones/src/recharge.rs` 新增）

```rust
pub struct PayMethod { pub code: String, pub payid: String, pub name: String, pub nopassword: bool, pub remark: Option<String> }
pub struct PasswordPad { pub uuid: String, pub keys: Vec<String> }      // 只用于渲染；禁止还原
pub struct RechargeOrder { pub order_id: String, pub status: u8, pub pay_exp_date: Option<String>, pub tranamt: Option<f64> }

pub async fn create_order(client, feeitem_id: &str, tranamt: &str, third_party: Option<&str>) -> Result<String>
pub async fn fetch_pay_methods(client, order_id: &str) -> Result<(RechargeOrder, Vec<PayMethod>)>
pub async fn query_account(client, order_id: &str, pay: &PayMethod) -> Result<(Vec<String>, Vec<String>, Option<PasswordPad>)>
pub async fn submit_pay(client, order_id: &str, pay: &PayMethod, accountno: &str, ccctype: &str, password_seq: Option<&str>, uuid: Option<&str>) -> Result<()>
pub async fn fetch_order_status(client, order_id: &str) -> Result<(RechargeOrder, Vec<PayMethod>)>
pub async fn cancel_order(client, order_id: &str) -> Result<()>
```
- 全部走 `Envelope` 里的 charge 系信封解析（`code==200` 成功），`synjones-auth` 与 Basic 头由 client 统一注入（Basic 作为常量集中一处，附注释说明它是公开硬编码、来源 bundle）。
- **单测**：用内联 JSON 样本断言解析（订单/支付方式/accountno 两种形态/ccctype/passwordMap）；断言「只保留 ACCOUNT/ACCOUNTTSM」的过滤；断言 `nopassword` 的三态处理。

### 2.2 命令层（`commands/electricity.rs` 追加，或新 `commands/recharge.rs`）

`recharge_create` / `recharge_pay_methods` / `recharge_query_account` / `recharge_submit` / `recharge_status` / `recharge_cancel`。
- 入参出参全 camelCase；失败文案可读（沿用 `CommandResult` 三态）。
- **`password_seq` 与 `uuid` 只在一次调用内存在**，不写任何持久化、不进日志。

### 2.3 前端（`PowerPanel` 充值流程）

1. 房间已选 + 金额输入（快捷金额 `layout`、范围 `retain_money`…`maxmoney` 提示）
2. **风险声明**（常驻在充值区块内，见 §2.4）→ 勾选/确认后方可继续
3. 点「立即充值」→ `recharge_create` → `recharge_pay_methods`
   - `order.status==1` → 已完成，直接给结果
   - 无可用账户类支付方式 → 明确报错（不展示第三方渠道）
4. 免密（`nopassword`）→ 显示「确认支付 ¥X」→ 提交
   需密码 → 渲染**安全键盘**（按 `keys` 顺序显示 10 键、点满 6 位自动提交，提交的是**下标序列**）
5. 轮询 `recharge_status`（2s × 最多 15 次 ≈ 30s）→ `status==1` 成功；超时判失败并提示可取消
6. 失败/放弃/超时 → 提供「取消订单」；离开页面时清理定时器
7. 保留「去官网充值」（`open_recharge_in_browser`）作为兜底入口

### 2.4 风险声明文案（用户明确要求，界面常驻）

> **充值会真实扣款，且不可撤销。**
> · 本功能直接调用学校官方缴费接口，金额与房间信息以学校系统返回为准。
> · **客户端不接触、不保存你的校园卡密码**：密码在你点击的键盘位置上加密校验，由学校系统完成比对。
> · 下单成功后若未完成支付，可点「取消订单」释放；已扣款项请以学校官方系统记录为准。
> · 学校接口若调整，本功能可能失败——此时请用「去官网充值」。
