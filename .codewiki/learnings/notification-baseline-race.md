# 通知基线与已读竞态教训（M5 复核修复，2026-09-20）

三个问题都是「跨 await 的状态生命周期」与「用代理信号代替显式语义」这两类病的变体，
复核阶段（用户裁决后逐条过）修掉。写通知类「后台轮询 + 本地状态文件」功能时按此对照。

## P0 已读复活：轮询快照整份回写覆盖用户已读

**现象假设**：`poll_tick` 每轮开始时 `load_state` 得到快照 `st`，随后发起网络拉取
（await 点）；期间用户在前端「标已读」并落盘（`unread` 减少）；轮询醒来后把**整份
旧快照** `save_state` 回写——用户刚读掉的通知被旧快照原样「复活」，下次启动又在
未读列表里出现。

**修复**（`commands/notification.rs:72-75`）：**落盘前重新 `load_state`**，未读列表
以盘上最新为准、只把本轮 `fresh` 追加其上；游标与基线标志按快照覆盖（每源游标只由
轮询单写者维护，无并发写方）。规则提炼：**「读快照 → await → 写回」模式里，await
之后盘上状态可能已被别的写方改变；整份回写前必须重读，或把回写收窄为「只写本写方
拥有的字段」**。`st` 快照的 `unread` 在修复后不再参与落盘（注释明说「不再使用」）。

## P1 首条待办被吞：「游标为空」不能当「未基线」的代理信号

**现象**：基线语义最初靠「游标为空 = 该源从未拉过 = 本轮建基线不通知」推断。待办源
**空页起步**：首轮拉到 0 条 → 游标仍为空 → 第二轮拉到第 1 条真待办时仍被判为
「首轮」→ 被当基线吞掉，用户永远收不到第一条待办通知。

**修复**：`NotificationState.baselined_sources: BTreeSet<String>` **显式基线标志**
（`infra/notification.rs:103`），`diff_seen` 的 `already_baselined` 参数改为显式
布尔（`:231`）：未基线时无论 fetched 有无都只建游标不通知、返回 `baselined=true`
让调用方把源 key 写进标志集合（`:227-238`）。规则提炼：**「集合为空」是状态不是
事件，用它推断「从未发生 X」在空态合法的领域（空列表源）必然误判；事件型语义
（「建过基线」）要显式存标志**。

**serde 迁移坑**：旧版本文件没有该字段 → `#[serde(default)]` 空集，若按「空 = 未
基线」处理，所有老用户升级后首轮会把基线前的存量条目**全部当新通知轰炸**。迁移
口径（`diff_seen` 头注 `:227-230`）：调用方以「**游标非空**视作已基线」补写标志——
旧文件里游标非空 ⇔ 至少拉过一轮 ⇔ 基线事实上已建（旧实现建基线时写入全量游标）。
单测 `:534-543` 钉住该迁移语义。教训：**给存量文件补显式标志时，要找一个与旧实现
行为等价的判定式做一次性回填，而不是接受「标志缺失 = 初始态」的字面语义**。

## P1 托盘失败锁死：关窗拦截的前提是「有地方可唤回」

**现象假设**：关窗 = 隐藏到托盘的逻辑无条件拦截 `CloseRequested`；若托盘创建失败
（缺 icon 资源 / 平台限制），窗口被藏起且没有任何托盘图标可点——应用既不可见也
退不出，只能任务管理器杀。

**修复**（`app_tray.rs:28` + lib.rs 的 `on_window_event`）：`TRAY_READY: AtomicBool`
显式记录托盘建成与否，`build_tray` 成功才 `store(true)`（`app_tray.rs:86`）；关窗
拦截以 `TRAY_READY.load() == true` 为前提，未建成走默认关闭退出（宁可退出也不假死）。
规则提炼：**「把入口藏到另一个地方」的功能，必须先确认目的地存在才生效**——拦截
默认行为前，替代路径必须已验证可用。

## 附：为什么这类 bug 在复核阶段才暴露

三个问题在实现时都有「单轮测试通过」的表现：P0 需要轮询 await 窗口内恰有用户操作、
P1 需要待办源恰好空页起步、P1 托盘需要托盘恰好创建失败——都是**环境时序依赖**而非
纯逻辑错，单测与快速手验不易命中。对策已落进代码：diff_seen / push_unread /
elec_should_alert 全部做成纯函数（`infra/notification.rs`），时序类问题靠单测
枚举状态组合（空游标 × 未基线 × 非空 fetched 等）钉死，而非依赖手验碰场景。
