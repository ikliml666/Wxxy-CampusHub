# 调课通知 L1/L2 分级口径与 noticeId 取舍（M2.5 批次 3）

## 背景

冻结契约 §2.5 只规定了 L1 提取要素清单与 L2 的 High 条件（「课程名精确匹配唯一一门且周次、星期、节次齐全」），真实通知文本的形态歧义与 `CourseOverride` 的写入细节需要就地裁决。

## 决策

1. **课程名匹配 = 对本地课程名做 contains 扫描**（而非独立提取名字再比对）：通知文本没有可靠的名字边界（「信息安全课程」「《信息安全》」混排），contains 对书名号/前后缀形态天然命中。多名命中时**裁剪被长名包含的短名**（文本含「信息安全实验」必含「信息安全」，短名不是独立意图）；裁剪后仍多名 → Low「通知中出现多门课程」由用户分次粘贴或手动选择。唯一名但多门同名课（不同班级）→ Low「匹配到 N 门同名课程」。
2. **单次解析只产出 1 个候选**：契约 `Vec<NoticeCandidate>` 容纳了多候选的可能，但手动粘贴场景一次贴一条（M5 接公告流后按公告条数天然拆分）；教务通知多条调整混排属遗留项。
3. **新时间/新教室 = 箭头词之后优先、全文回退**（`after_adjust_arrow`，12 个箭头词如「调整到/调至/改到/换到/更换为」）：调课通知「由周一3-4节调整到周四5-6节」的第一个星期/节次是**旧值**，直接取全文第一个会拿到「周一」——实测样例测出该问题后加入。周次/星期/节次/教室四个提取器统一 tail 优先；箭头后缺表述时回退全文（「周一3-4节 由 D4-207 调整到 D4-305」星期仍在全文）。周次不受「原周次→新周次」双表述影响（首个区间/单周匹配优先级已足够，极端场景降级 Low 由用户确认）。
4. **单节强制「第」前缀**：`第3节` 命中，`3节` 不命中——避免「共16节课」「3节连上」这类**节次数表述**被误提为调课节次。区间 `3-4节` 无此前缀（契约明确形态）。同理周次区间 `3-4周` 优先于单周扫描（否则「3-4周」被拆成单周 4）。
5. **停课通知的星期/节次原样保留进 override**：契约未细化停课的 `new_*` 语义，model.rs 原注释写「停课时为 None」。实际语义需要 day 定位「停哪一次」——一周多节次上课的课程（周一、周三各一次）只停通知指定那次，None 无法表达。已改为：调课/补课 = 新时间，停课 = 被停那次的星期/节次（供前端定位），通知未提及时才为 None；`new_position` 停课通知通常无值自然为 None。model.rs 注释同步更新。
6. **noticeId = `manual:<16 位十六进制>`，用 `DefaultHasher` 而非 sha256**：契约建议「sha256 前 16 位」，但为哈希正文引入 `sha2` 依赖不值得——`DefaultHasher::new()` 是零密钥 SipHash，**同进程/同版本 std 确定性**，满足「同一通知重复粘贴 noticeId 稳定（去重）+ 撤销键」的全部需求；**非密码学哈希**（通知正文无对抗场景）。跨 Rust 版本的稳定性无保证——真要跨版本迁移时 override 已落库，撤销靠精确字符串匹配不受影响。M5 接公告流时改用公告 id，`manual:` 前缀即区分来源。
7. **`apply_override` 校验 courseId 必须落在本地课程**：低置信候选 course_id=None（用户在 UI 手动选课后再采纳，前端把选定 id 塞回 candidate）或课程已删 → 业务失败，绝不写孤儿 override。`delete_course` 已级联清理 override（批次 2 决策），三层不变量闭合。
8. **幂等口径 = `noticeId + courseId` 覆盖**：同一通知对同一课程重复采纳 → 覆盖旧叠加（保留 `ov-` 新 id）；同一通知对**不同课程**的采纳并存（一次通知调整多门课的合法形态）。`revoke_notice` 按 `source_notice_id` 整批删除，0 条也返回 0 幂等成功。
9. **「本周」解析依赖 `current_week` 锚点**：`parse_notice` 命令层用 `chrono::Local::now()` + `campus_schedule::current_week`（开学日 + 总周数夹逼）现算；开学日未配置/假期越界 → None → 通知含「本周」时降级 Low 并写明「无法确定当前教学周」，**绝不猜周次**。
10. **类型关键词不影响置信**：High 条件是课程唯一 + 周次/星期/节次齐全（契约口径），未识别到调课/停课/补课关键词时默认 `Rescheduled` 但不降级——类型判断错误（把停课当调课）会在用户确认环节暴露，且 L1 关键词词表本就有限，把「无关键词」当降级会让大量平实表述（「上课地点改为…」）进待确认，噪声大于收益。

## 教训

- 「取文本第一个匹配」在调课通知里天然错位——通知结构是「旧值 → 箭头 → 新值」，所有面向新值的提取必须先切箭头后的 tail；单测样例「由周一3-4节调整到周四3-4节」当场抓住了该缺陷。
- 数字锚定扫描（`match_indices('周'/'节')` + 往左收 ASCII 数字）在 UTF-8 下安全的前提：只按 ASCII 字节判定与切片（多字节字符各字节 ≥0x80），`text[..start].ends_with('第')` 这类边界检查回到 char 层做。
